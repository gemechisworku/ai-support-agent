Architecture, system design and infrastructure

POC on one Mac (Apple M4, 16 GB, macOS) · Open source first · 5 November 2026

1Architecture at a glance

The design follows the production pattern from Document 1, with three deliberate boundaries. Media (LiveKit) is separate from reasoning (the agent worker), and reasoning is separate from data (the gateway). The agent can reach bank data only through a small set of gateway tools, and only for the customer it has verified on that call. Contact rules are enforced by the scheduler before a call exists, so the model cannot override them.

2Key flows

Outbound missed-payment call

  1. The scheduler asks the gateway (service scope) for accounts 1–30 days past due, then filters them through the compliance gate: local calling window, frequency cap, do-not-call list, consent, open disputes and cease-contact flags.
  2. For each eligible account it creates a LiveKit room with metadata (call_id, campaign, loan_id) and calls CreateSIPParticipant, which routes the call through Asterisk to the customer’s softphone.
  3. LiveKit dispatches an agent worker into the room. The worker opens a gateway session bound to call_id; the customer is still unverified.
  4. The agent runs the state machine: AI and recording disclosure, right-party check, then verification through the verify_identity tool. If verification succeeds, the gateway binds that one customer_id to the session.
  5. The agent explains the overdue amount (get_loan_status), asks for the reason, explains consequences (search_policy), and records the outcome (record_promise_to_pay or request_callback).
  6. For escalations it calls escalate, which writes a ticket with a summary, and transfers the call by SIP to the human extension.
  7. When the call ends, the worker writes the structured outcome, the transcript is redacted, and traces are flushed to Langfuse.

Inbound call

The customer dials support extension 100. Asterisk forwards the call to LiveKit SIP, a dispatch rule creates a room, and an agent joins. The caller’s number is used only as a hint for candidate customers. General policy questions are answered without verification; anything account-specific triggers verification first.

3Agent design

Each state is a LiveKit Agents Agent with its own short instructions and only the tools it needs. Hand-offs between states are explicit function returns. Small local models stay on track because each prompt is short and each state has at most three or four tools. Global “interrupt” intents (human, dispute, stop calling, a third party on the line, a lawyer or bankruptcy) are checked on every turn and override the current state.

Gateway security rules. No free-form queries; every tool has typed inputs. The session token comes from the dispatcher, not the model. Customer ids are never accepted from the model after binding. Responses contain only the fields the state needs, with full account numbers and national IDs masked. Each call is rate-limited and audited (who, what, when, result). Tool outputs are treated as data, not instructions, which guards against prompt injection. The agent can write only to interaction tables, never to balances.

5Policy knowledge base (embedded)

About 20 synthetic Markdown policy documents, each with front-matter (doc_id, title, product, version, effective_date, audience):

  • Product terms, one per loan product
  • Repayment schedules and due-date rules
  • Grace periods, late fees and penalty interest
  • Delinquency stages and consequences (reminders, fee, bureau reporting at 30 days past due, collections at 60, default at 90)
  • Hardship assistance and restructuring (eligibility; humans decide)
  • Promise-to-pay rules (maximum 14 days, partial payments)
  • Payment channels and posting times
  • Early repayment and payoff
  • Disputes and error resolution
  • Identity verification and privacy procedure
  • Complaints and escalation procedure
  • Contact and calling rules (also read by the scheduler as configuration)
  • Required disclosures (versioned script text)
  • Frequently asked questions

Ingestion: documents are split by heading into chunks of about 300–500 tokens with section paths, embedded with nomic-embed-text (768-dimensional) via Ollama, and stored in PostgreSQL with pgvector (HNSW index) alongside a tsvector column for keyword search. Retrieval: hybrid vector and full-text search merged with reciprocal rank fusion, filtered by product and effective date, returning the top 4 chunks. If the best score is below a threshold, the agent says it will follow up rather than guessing. Re-ingesting a new document version keeps the old version for audit. Here “embedded” means vectorised; if you meant an in-process store with no server, LanceDB or sqlite-vec fit the same interface.

Known risks. SIP and RTP over Docker networking on macOS can be fiddly. We publish a fixed RTP port range and pin the advertised IP, and can fall back to running Asterisk natively with Homebrew. LiveKit’s browser playground is a no-telephony fallback for testing the agent from day one.

7From POC to production

TelephonySwap Asterisk for a carrier SIP trunk, register numbers, add answering-machine detection and caller-ID reputation (STIR/SHAKEN).
ScaleLiveKit cluster or LiveKit Cloud; agent workers autoscaled on Kubernetes; GPU inference servers (vLLM) or managed STT, LLM and TTS to reach about 800 ms.
Bank integrationPoint the gateway at the real core-banking and CRM APIs behind the bank’s API gateway with mTLS and OAuth service identities. The agent’s code is unchanged.
GovernanceJurisdiction-specific rules in the policy configuration, legal review of disclosures, retention policies, encrypted recordings, sampled human QA, and a model-risk review.
